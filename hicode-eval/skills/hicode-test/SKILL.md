# HiCode 批量评测

使用 `hicode-eval/eval.sh` 与现有单一看板（默认 8878）。每题独立尝试一次、自动判题；不使用人工 continue/review 或不存在的通知命令。

## 找到当前代码与记录

先解析 Skill 目录的真实路径，再向上定位包含 `hicode-eval/src/cli.ts` 的 checkout。`eval.sh` 是稳定入口；实现位于 `src/host/`、`src/worker/`、`src/web/`，通用配置位于 `config/`。仓库顶层的 `src/` 是被测 HiCode，不能把两者混淆。

个人题目状态、环境准备、临时选题和真实运行记录都在仓库外，不再查找 eval 内的 TASK-STATUS.md 或 expansion 配置。本机既有环境的定位线索见 [本机环境](references/local-environment.md)；首次接手或跨窗口操作时读取，已有路径未变时不反复读取。

## 先确定这次要做什么

- **启动测试**：确认已就绪题目和服务 → 批量提交 → 核对一次已运行 → 给出页面、批次 ID 和预算。
- **分析已有结果**：一次读取状态汇总，只查异常证据，不因此创建或重跑任务。
- **准备新题 / 修框架**：只有用户要求时进入。与真实测试分开交付，不把“跑一批”扩成边跑边开发。
- 用户问 Codex 自身耗时，就说明自己的检查、工具执行和等待耗时；不把问题偷换成 HiCode 做题表现，也不因此操作正在运行的任务。

## 快速启动规则

1. 一次核对 Git 状态/目标 SHA、现有服务身份与 data-dir、所选题目就绪记录、模型配置和服务并发上限。优先复用同一页面、数据根、源码 payload 和已验证依赖。读取过且未变化的文件不反复读取。
2. 保留用户选定的题目、模型、并发和权限策略。未指定并发时用 2；已指定 3 时按 3 配置服务和批次。某题资源要求较高，只针对该题安排，不自动将整批串行。
3. 研发评测默认 1800 秒；未另指定时，对上游需要更长时间的题使用 `max(1800, task.agent.timeout_sec)`，例如 Scheme 2400 秒。不要擅自把其他题缩短到 900 秒。正式基准复现按用户要求使用上游时限，并记录实际条件。
4. 一轮测试提交一个批次，`tasks` 为 `{id, agentSeconds}` 对象数组；每题分别设置时间，不按预算拆批次。省略时限使用服务默认 1800 秒；遵守用户选择的原题或研发预算，全局并发限制仍生效。
5. 真实运行前简述题目、固定版本、实际模型服务、并发及预算；已有授权继续有效。Key 只供鉴权，日志/批次配置只记录环境变量名。提交超时先查是否已落盘，不能盲目重提。
6. 记录提交返回的 batch/run ID，核对一次模型、payload、运行/排队数量。仅要求“启动/挂起来”时，确认启动后交付，不占着回复循环等待整批结束；明确要求监督或分析到结束时才使用有界等待。

只有需要启动、提交、恢复或查证据时，读取 [操作与证据入口](references/operations.md)。不要为了普通状态查询通读源码、所有历史日志或其他技能。

## 就绪与验证

- **采用批量快检，不逐题人工试跑。** 一次核对所选题的文件/哈希、输入路径、预算与必要命令/库；相同环境和依赖按组检查并复用结果。快检通过就交给调度器，不为每题先启动模型、跑基线/参考解、亲自实现一份答案或演练整个验收流程。仅快检失败或真实执行出现异常时定点查证。
- `config/terminal-bench.json` 中存在 ID 不代表题目就绪。复用已记录的输入映射、必要依赖、原始初始化/判题支持以及版本依据；缺项明确列为待适配，不能假称全部可运行。
- 不为凑够数量擅自换题。不能手绘替换原图、改字体/坐标、改题面、改原断言，或放宽判题来绕过准备问题。已有基准输入和判题的语义必须保留；确需改条件时先说明并取得用户选择。
- 正常提交、状态归档、文档或技能更新，不重建环境、不跑全仓验证。修改实现才按仓库要求验证；若测试已通过而后续类型检查失败，修正后补跑受影响测试及失败阶段，不机械重复已通过的全部阶段。
- 题目独立尝试一次，结束后由原 verifier 判分；不追加人工纠错提示，不自动重试未通过题。模型失败、环境/框架阻塞、用户取消分别记录。

## 运行与异常

- 调度、补位、计时和自动判题交给现有服务。Codex 不每几秒查询一次，不为看日志另建服务、换端口或新开数据根。
- 当前 hicode-eval 没有 Codex 完成通知桥接，也没有运行中修改并发的 API。不得宣称已绑定通知、能后台唤醒或能无损热改并发。服务重启会取消活动任务，不能为改并发直接重启。
- 用户询问状态或表达不满不等于取消授权。不得因此取消批次、杀进程、重跑题或变更权限；只有明确取消要求，或有具体即时安全风险需要制止时才停止任务。
- 普通题目失败由调度器补位；`needs_recovery`、审批等待、缺依赖等标记为阻塞并保留证据。当前调度器对 `needs_recovery` 会全局停调度，不能声称其他题必然继续。能用现有 recover 核验收尾就处理；否则准确报告受阻范围，不擅自取消整批或放开权限。
- 用户要求全程监督时，以几十秒级有界 wait 观察状态变化，每轮只输出批次计数和异常摘要。长时间无变化先检查审批/模型/工具状态，不凭静止的 TUI 判定挂死。

## 结果归档

在外部数据目录复用一份题目状态清单，分为已通过、未通过、待测试；未通过项另标模型未达标、框架/环境阻塞或超时。取消且未执行的题仍待测试，失败后通过保留两次尝试，不能覆盖历史分数。

通过要求 execution=completed、grading=passed、证据已收集。超时但判题通过单独标注，不能算完整通过。正常通过项写结果即可；异常项读对应 TUI/events、判题输出和必要请求片段，归属不清就保留不确定性。

交付包含本批计数、题目结果、主要异常、实际预算和日志位置。复盘优先回答框架哪里受阻、模型哪里答错；不重新遍历已审完的正常日志，不自动 commit/push。
